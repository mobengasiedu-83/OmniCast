# OmniCast — Implementation status & module register

The single source of truth for which phases, modules and integrations have been applied to this
repository, and what is still outstanding. It is a living document: **update it in the same change
that installs or applies a module.**

- Document owner: platform team
- Spec source: `GWO_SEVO_OmniCast_Admin_and_Client_Development_Phases.docx` (20 phases)
- Last updated: 2026-11-05

## How to keep this file current

1. When a module is applied, move its row from **Remaining** to **Applied** in the phase section and
   append a line to the [Changelog](#changelog).
2. When a package or provider integration is added, list it under **Applied modules** for that phase
   (name + version + why).
3. When a phase reaches its acceptance gate, change its status in the overview table to `Done` and
   record the verification evidence (test names + command output).
4. Never mark a row `Done` on scaffolding alone: the acceptance gate in the spec must pass.

## Phase 12 — Scheduling & delivery orchestration

| Module | State |
| --- | --- |
| Queue topology: `config/queues.php` names the `campaigns` queue that orchestrates multi-channel passes and the `sms` / `voice` / `email` queues a single-channel campaign and its retries travel on, so a rate-limited aggregator, a slow PBX or a throttled relay can never starve the other channels. Every channel carries its own `cps` ceiling (seeded from `SMS_BROADCAST_GLOBAL_CPS`, `VOICE_BROADCAST_GLOBAL_CPS` and `EMAIL_BROADCAST_GLOBAL_CPS`, zero meaning "as fast as the provider answers"), plus the `tries`, `backoff` and `timeout` a worker applies; `queues.jobs.campaign_dispatch` does the same for the dispatcher itself, and `queues.scheduler` / `queues.failed` hold the stall threshold, sweep batch size and failed-job retention | ✅ |
| Horizon supervisors: `config/horizon.php` now runs five supervisors on the `redis` connection — `supervisor-campaigns` (`campaigns`), `supervisor-sms`, `supervisor-voice`, `supervisor-email` and `supervisor-default` — all balanced by `auto`/`time`, with a per-supervisor `timeout` that mirrors the queue policy (120 s SMS, 300 s voice, 180 s email, 60 s default) and production `maxProcesses` of 10 / 16 / 8 / 6 / 4 against 2 / 2 / 1 / 1 / 1 locally, so a long voice call cannot be killed on the timeout that suits a Mailable | ✅ |

| Dispatch job: `DispatchCampaignJob` reads its `tries` and `timeout` from `queues.jobs.campaign_dispatch`, returns the exponential `backoff()` escalation, and sets `failOnTimeout` so a hung pass is failed and picked up by the sweep instead of being released with no progress. | Delivery pacing: `DeliveryPacer` holds each channel to its negotiated submissions per second through a shared `Illuminate\Cache\RateLimiter` (`delivery-pace:<channel>`), resolving the ceiling as client override → platform `rate_limits.<channel>_cps` → `queues.channels.<channel>.cps`, with zero (or absence) meaning unthrottled. | Stalled sweep: `campaigns:sweep` (`--limit` defaults to `queues.scheduler.sweep_limit`) re-queues `Running` campaigns that still have `pending`/`queued` recipients and have not moved for `max(stalled_after_minutes, retry_delay_minutes + 5)` — the extra window is what keeps a deliberately delayed retry pass from being mistaken for a stall.
